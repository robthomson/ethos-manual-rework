# 版本管理

Ethos 目前以版本号形式发布固件（1.6.x），并已表明将转向以年份命名的品牌形式（例如 "Ethos26"）。本手册需要在新版本内容正在积极编写的同时，保持旧版本文档依然可用且正确——本页说明的就是实现方式。

## 工作原理

版本管理由 [mike](https://github.com/jimporter/mike) 处理，这也是 Material for MkDocs 官方推荐的工具。`.github/workflows/deploy.yml` 运行 `mike deploy`，而不是直接发布到 `gh-pages` 根目录：每个版本都会被构建并提交到该分支下各自的子目录中（`/1.6/`、`/26/` 等），而 `manual.rt-rc.com/` 会重定向到当前持有 `latest` 别名的那个版本。Material 会自动显示版本选择下拉菜单，其内容读取自 `versions.json`（由 `mike` 维护）——这与语言切换器互不相关，且能良好地组合使用：版本是外层路径片段，语言（一旦出现除 `en` 之外的语言）是内层路径片段，例如 `manual.rt-rc.com/26/fr/...`。

这里复用了与 [PR 预览](index.md#pr-previews)相同的"在 `gh-pages` 上使用子目录"机制——`mike` 的版本目录与 `pr-preview/` 目录可以在同一分支上共存而不冲突，因为两者各自只会操作自己的路径。

## 源码布局：`main` + 冻结分支

- **`main` 始终跟踪当前/最新固件版本的内容。** 日常编辑就在这里进行，与现在完全一致——常规的贡献流程没有任何变化。
- 一旦新固件版本的手册需要开始与 `main` 上的内容产生分歧，**先为旧版本切出一个以其命名的分支**，例如 `1.6`，将其永久冻结。此后 `main` 就成为新版本的内容。
- 冻结分支并非就此废弃——它仍然可以通过自己的 PR 接收修正。只是不再跟踪新版本的开发。

## 切出新版本

当下一个版本的手册需要开始编写时（例如 Ethos26）：

1. 从 `main` 创建并推送要被留在过去的那个版本的冻结分支：

   ```
   git checkout main && git pull
   git branch 1.6
   git push origin 1.6
   ```

   `1.6` 分支上的 `.github/workflows/deploy.yml` 副本此后会在每次推送到该分支时永久执行 `mike deploy --push --update-aliases 1.6 latest`——保持原样即为正确，无需修改，因为分支是一份完整快照，其中包含它自己的 CI 配置。

2. 在 `main` 上编辑 `.github/workflows/deploy.yml`：将 `Deploy version 1.6 with mike` 步骤中的版本字符串（以及该步骤的名称）从 `1.6` 改为新版本的标签（例如 `26`）。这是开始部署新版本所需的**唯一**修改——下一次推送到 `main` 就会将其发布到 `/26/` 并把 `latest` 别名移到那里，而 `/1.6/` 则保持原样不变。

3. 根据实际变化更新 `main` 上新版本的内容——新增/重命名的菜单章节、新的截图、更新的术语。各分支之间 `mkdowns.yml` 的 `nav` 可以自由地不同；不存在需要保持同步的共享配置。

4. 如果针对新分支的 PR 也需要获得实时预览，请将该分支名称添加到 `.github/workflows/pr-preview.yml` 的 `branches:` 触发列表中（冻结分支通常不需要这一项，因为它们只偶尔接收修正 PR）。

## 跨版本的截图

截图是从特定的 Ethos 构建版本中捕获的（参见[截图流程](screenshot-pipeline.md)），并且属于其所展示界面对应的那个分支——切出版本时，截图集合自然会随其他所有内容一起分叉，因此在分支点之后，`1.6/assets/` 与 `main` 的 `docs/en/assets/`（一旦为新界面重新生成）就会各自独立地演进。
