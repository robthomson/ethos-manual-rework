# ניהול גרסאות

כיום Ethos מופצת עם קושחה הנושאת מספרי גרסה (1.6.x), ונרמז על מעבר למיתוג
מבוסס שנה (למשל "Ethos26"). מדריך זה צריך לשמור על התיעוד של גרסאות קודמות
זמין ונכון, בעוד תיעוד גרסאות חדשות נכתב באופן פעיל — עמוד זה מסביר כיצד.

## איך זה עובד

ניהול הגרסאות מטופל על ידי [mike](https://github.com/jimporter/mike),
הכלי ש-Material for MkDocs עצמו ממליץ עליו. `.github/workflows/deploy.yml`
מריץ `mike deploy` במקום לפרסם ישירות לשורש `gh-pages`:
כל גרסה נבנית ומבוצע לה commit לתיקיית משנה נפרדת שם (`/1.6/`,
`/26/`, …), ו-`manual.rt-rc.com/` מפנה לגרסה שמחזיקה כרגע את הכינוי `latest`.
Material מציג אוטומטית תפריט נפתח לבחירת גרסה, שקורא את `versions.json`
(אותו `mike` מתחזק) — הדבר אינו קשור למחליף השפות, ומשתלב עמו בצורה נקייה:
הגרסה היא מקטע הנתיב החיצוני, והשפה (ברגע שתתקיים יותר מ-`en`) היא
המקטע הפנימי, למשל `manual.rt-rc.com/26/fr/...`.

מנגנון זה עושה שימוש חוזר באותו מנגנון "תיקיית משנה ב-`gh-pages`" כמו
[תצוגות מקדימות של PR](index.md#pr-previews) — תיקיות הגרסאות של `mike`
ותיקיית `pr-preview/` מתקיימות יחד באותו ענף בלי להתנגש, מכיוון שכל אחת
נוגעת רק בנתיבים שלה.

## מבנה המקור: `main` + ענפים מוקפאים

- **`main` תמיד עוקב אחר התוכן של גרסת הקושחה הנוכחית/העדכנית ביותר.**
  העריכה היומיומית מתבצעת כאן בדיוק כפי שהיא מתבצעת כיום — דבר אינו משתנה
  בתהליך התרומה הרגיל.
- ברגע שהמדריך של גרסת קושחה חדשה צריך להתחיל להיפרד ממה שקיים ב-`main`,
  **יש ליצור תחילה ענף בשם הגרסה הקודמת**,
  למשל `1.6`, כדי להקפיא אותה לעד. לאחר מכן `main` הופך להיות התוכן של
  הגרסה החדשה.
- ענף מוקפא אינו מת — הוא עדיין יכול לקבל תיקונים דרך ה-PR-ים שלו. הוא רק
  אינו עוקב עוד אחר פיתוח הגרסה החדשה.

## יצירת גרסה חדשה

כאשר יש להתחיל את המדריך של הגרסה הבאה (למשל Ethos26):

1. מתוך `main`, צרו ודחפו את הענף המוקפא עבור הגרסה שנשארת מאחור:

   ```
   git checkout main && git pull
   git branch 1.6
   git push origin 1.6
   ```

   העותק של `.github/workflows/deploy.yml` בענף `1.6` מבצע מעתה לעד
   `mike deploy --push --update-aliases 1.6 latest` בכל דחיפה לאותו
   ענף — נכון כמו שהוא, אין צורך בעריכה, מכיוון שענף הוא תצלום מלא
   הכולל את תצורת ה-CI שלו עצמו.

2. ב-`main`, ערכו את `.github/workflows/deploy.yml`: שנו את מחרוזת הגרסה
   בשלב `Deploy version 1.6 with mike` (וגם את שמו) מ-`1.6` לתווית של
   הגרסה החדשה (למשל `26`). זו העריכה **היחידה** הנדרשת כדי להתחיל
   לפרסם את הגרסה החדשה — הדחיפה הבאה ל-`main` תפרסם אותה ל-`/26/`
   ותעביר לשם את הכינוי `latest`, בעוד `/1.6/` יישאר בדיוק כפי שהיה.

3. עדכנו את התוכן של הגרסה החדשה ב-`main` בהתאם למה שהשתנה בפועל —
   מקטעי תפריט חדשים או שהשם שלהם שונה, צילומי מסך חדשים, טרמינולוגיה
   מעודכנת. ה-`nav` של `mkdocs.yml` יכול להיות שונה לחלוטין בין ענפים;
   אין תצורה משותפת שצריך לשמור מסונכרנת.

4. הוסיפו את שם הענף החדש לרשימת הטריגרים `branches:` שב-`.github/workflows/pr-preview.yml`
   אם רוצים ש-PR-ים מולו יקבלו גם תצוגות מקדימות חיות (ענפים מוקפאים
   בדרך כלל אינם זקוקים לכך, מכיוון שהם מקבלים רק PR-ים מזדמנים של תיקונים).

## צילומי מסך בין גרסאות

צילומי המסך נלקחים מבנייה ספציפית של Ethos (ראו [צינור צילומי המסך](screenshot-pipeline.md))
ושייכים לענף שאת ממשק המשתמש שלו הם מציגים — יצירת גרסה מפצלת באופן טבעי
את אוסף צילומי המסך יחד עם כל השאר, כך ש-`1.6/assets/` ו-(לאחר יצירה מחדש
עבור הממשק החדש) `docs/en/assets/` שב-`main` מתפצלים באופן עצמאי לאחר
נקודת ההסתעפות.
